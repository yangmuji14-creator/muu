# 第一部分　「新建角色 · 性格」字段的产品设计判断

## 1.1 现状还原（读码 + 实跑确认）

**交互路径**

1. 用户在 `ContactsPage.svelte:803-818` 的 `.tag-cloud` 里点 20 个标签中的任意个，无数量上限（`toggleTag()` `:342-346` 纯数组增删）
2. 点「创建」→ `createPersona()` `:482-512` 提交 `{name, description, personality}`
3. 后端 `webui/routes/persona.py:178-183`：`apply_persona_tags(persona.model_dump(), personality)` 把标签翻译成 `speaking_style` / `emotional_patterns` / `relationship_behavior` 三个 dict（外加 `hard_rules` 列表），`Persona(**merged)` 落盘
4. **弹窗关闭、表单重置，用户从头到尾看不到翻译结果**

**第一处硬伤：标签云没有样式。**
`.tag-chip` / `.tag-cloud` / `.tag-hint` 三个类在全部 `.svelte`、`settings-base.css`、`tokens.css` 里**零 CSS 规则**（`grep -rn "tag-chip\|tag-cloud\|tag-hint" webui/frontend/src` 只命中 `ContactsPage.svelte:806/807/810/828` 四处模板本身）。构建产物 `webui/static/assets/index-C0nlL5Bx.css` 里 `grep -o "\.tag-[a-z]*"` 也是零命中，而同一份 CSS 里 `.roster-tag` 命中——说明构建是最新的，不是漏构建。
→ 20 个标签实际渲染成**浏览器默认 `<button>`**（灰色凸起圆角块），`on` 类没有对应样式，`aria-pressed` 翻转对视觉零影响。**用户点选完全没有任何视觉反馈。**

**第二处硬伤：翻译表的字段名与消费端契约从未对齐。**

| 层 | 翻译表实际产出的 key（16 个） | `prompt_builder.py` / `promptFields.js` 认的 key | 命中 |
|---|---|---|---|
| `speaking_style` | 说话量、话题跳跃、表面反应、口头禅、语气、常用词、语气词、常用句式 | `基础风格` | **0/8** |
| `emotional_patterns` | 表达方式、依恋类型、情绪调节、触发点、情感表达 | `依恋类型`、`压力反应`、`爱的语言` | **1/5** |
| `relationship_behavior` | 争吵模式、日常互动、底线 | `冲突模式`、`边界需求` | **0/3** |

`prompt_builder.py:198` 只读 `speaking.get("基础风格","")`；`emotional_patterns` 只认三 key（`:218-223`）；`relationship_behavior` 只认两 key（`:260-263`）。翻译表**从不产出 `基础风格`**，所以「说话方式」这一组在多数标签下**一个字都进不了 prompt**。

**实跑输出（`./.venv/Scripts/python.exe` + `apply_persona_tags` → `Persona` → `PromptBuilder.build_stable`）**

| 选择 | 派生出的三组描述 | 实际进入 prompt 的身份行 | 进 prompt 字符 |
|---|---|---|---|
| `温柔` | 语气=温和耐心；常用词=[好的,没事的,慢慢来]；情绪调节=善于安抚 | `性格上，你温柔。你说话温和耐心。` | 8 |
| `傲娇` | 口头禅=[哼,才不是,随便你]；表达方式=明明在意却装作不在乎 | `性格上，你傲娇。` | **0** |
| `嘴硬心软` | 口头禅=[随便,无所谓,你管我]；争吵模式=嘴上说狠话但会偷偷关心 | `性格上，你嘴硬心软。` | **0** |
| `爱吃醋` | 触发点=[…]；底线=[…] | `性格上，你爱吃醋。` | **0** |
| `感性` | 表达方式 / 触发点 | `性格上，你感性。` | **0** |
| `脾气急` | 情绪调节 / 争吵模式 | `性格上，你脾气急。` | **0** |
| `粘人+缺乏安全感` | 依恋类型=焦虑型；触发点=[…]；日常互动=…；底线=[…] | `性格上，你粘人、缺乏安全感。情感上，依恋类型是焦虑型依恋。` | 15 |
| `话痨+高冷` | 说话量=话多，经常连发多条消息；话题跳跃=快；语气=平淡简洁；日常互动=被动等对方主动 | `性格上，你话痨、高冷。你说话话多，经常连发多条消息、话题跳跃快、平淡简洁。` | 39 |
| `温柔+活泼+细心` | 语气=温和耐心；常用词=[…]；常用句式=会主动提醒对方注意身体、天冷加衣 | `你说话温和耐心、会主动提醒对方注意身体、天冷加衣。` | 25 |

`话痨+高冷` 那行是**语义自毁**：同一个人「话多、经常连发多条消息」又「平淡简洁」，模型拿到互斥指令；而 `高冷` 真正的 `说话量="话少，回复短"` 被 `setdefault` 静默丢弃，用户完全不知道。
`温柔+活泼+细心` 那行是**语法不通**：把「常用句式」的值硬塞进 `你说话…` 的句式槽，读起来是病句。

## 1.2 四个风险项的实测结论

用户担心的四条，逐条用数据回答：

### ① 语义重叠 —— 成立，且比预想严重

- 20 个标签合并，**字段 key 冲突 26 次**，全部被 `setdefault` 静默丢弃（后到者失效，且不报错、不提示）
- **两两组合 190 对中 49 对（25.8%）存在 key 冲突** —— 用户随便点两个标签，四分之一概率有一半信息被吃掉
- 冲突热点：`relationship_behavior.日常互动` 被 **6 个标签**争用（粘人/高冷/活泼/爱撒娇/有主见/细心）；`speaking_style.语气` 被 **6 个标签**争用（高冷/温柔/活泼/理性/幽默/直球）；`emotional_patterns.表达方式` 被 4 个争用
- 存在**硬互斥对**：`话痨`(说话量=话多连发) ↔ `高冷`(说话量=话少回复短)
- 存在**标签内部自相矛盾**：`冷暴力` 的 `hard_rules` 写「生气时不可以使用冷暴力，要好好沟通」，同一标签的 `relationship_behavior` 又写「生气时沉默，已读不回」

### ② 描述爆炸 —— **不成立**（数据反向）

| 指标 | 实测值 |
|---|---|
| 单标签派生进 prompt | 0 ~ 21 字符（5 个标签为 0） |
| 常见 3 选进 prompt | 15 ~ 39 字符 |
| **全 20 个全选进 prompt** | **97 字符 ≈ 40 token** |
| 全 20 个合并后的存储体积 | 494 字符（单标签平均 91 字符，总表 1832 字符） |

结论：**「prompt 膨胀」是个伪问题。** 真正的问题是**反向的**——派生写得越多、丢得越多：全选 20 个标签，翻译表写了 494 字符，只有 97 字符活着进 prompt，**80% 的产出是死数据**。

### ③ 用户不可控 —— 成立，且是最致命的一条

- 创建后**没有任何入口**能回看/编辑/回滚派生结果；`GET /api/persona/tags` 只返回名字数组，无描述、无分组、无互斥信息
- 创建成功后 `showCreate=false` + 表单重置，**没有确认预览步骤**，用户是在完全黑箱的情况下按的「创建」
- 派生结果与「高级 Prompt」区的 `speaking_style`/`emotional_patterns`/`relationship_behavior` 是**两套并行入口**：`promptFields.js:59-135` 已经为这三个字段提供了完整可编辑 UI（`prompt-dict` 类型）。用户如果先在弹窗点标签、再去高级区改，**手填值会被 `setdefault` 保护**（这点是对的），但反过来——**建完再点详情页改性格，不会再触发任何派生**（详情页 `personality` 是 `type: 'list'` 的「每行一个」，`ContactsPage.svelte:132`）→ 同一个字段，两个控件，两种语义
- 多选无上限：可以点满 20 个，产出的是一坨自相矛盾的指令

### ④ prompt 膨胀 —— 不成立（见 ②）

## 1.3 明确结论

> **不要「保留原样」，也不要「整块砍掉」。结论是「降级为预填草稿」：把「点标签 → 系统自动翻译成三组描述」改成「点标签 → 预填三组描述的可编辑草稿 → 用户确认/修改后提交」。**
>
> 一句话：**保留标签作为「快捷输入」，废除「自动派生」这个对用户不可见、且 80% 无效的承诺。**

**为什么不是「保留原样」**：翻译表产出 16 个 key，**15 个不在契约内，命中率 1/16**；190 对组合 25.8% 静默覆盖；存在硬互斥与自相矛盾标签；用户全程不可见不可控。这套机制当前**净收益为负**——它让用户以为设置生效了，实际 5 个常见标签（傲娇/嘴硬心软/爱吃醋/感性/脾气急）一个字都没进 prompt。

**为什么不是「整块砍掉」**：标签本身是好东西。它是**降低填写门槛的输入法**——「傲娇」两个字比让用户手写「明明在意却装作不在乎」省事得多。`setup_wizard.py:439-466` 的 CLI 也在用同一份表，砍掉会让 CLI 与 WebUI 分叉。真正坏的是**「自动写进人设」这个副作用**，不是「标签」本身。

## 1.4 替代交互设计（可落地规格）

### 设计原则三条

1. **所见即所存**：标签点下去产生的任何文字，必须立刻在界面上可见、可改
2. **标签产出「人话」，不产出「字段」**：翻译表只负责把标签变成一句 ≤30 字的自然语言，落点必须是**契约内的 key**
3. **冲突必须显式**：同 key 冲突不再 `setdefault` 静默丢弃，改成合并成并列句 + UI 高亮提示

### 交互形态

```
┌─ 新建角色 ────────────────────────────────┐
│ 名字 *  [_______________________]        │
│                                          │
│ 性格（最多 3 个）            已选 2/3    │
│ ┌────────────────────────────────────┐   │
│ │ 温柔  活泼  细心  傲娇  高冷  话痨 │   │  ← 未选: 1px 描边 + text-2
│ │ 粘人  直球  幽默  理性  感性  大度 │   │
│ │ ...                                │   │
│ └────────────────────────────────────┘   │
│ ⚠ 「话痨」与「高冷」互斥，已自动取消「高冷」│  ← 互斥提示，非阻断
│                                          │
│ ▼ 这些会写进 TA 的人设（可改）            │  ← 折叠区，默认展开
│ ┌ 说话方式 ─────────────────────────┐    │
│ │ [温柔、话不多但很贴心___________] │    │  ← 可编辑 textarea
│ └───────────────────────────────────┘    │
│ ┌ 情绪反应 ─────────────────────────┐    │
│ │ [安全型；压力大时先自己待一会儿__] │    │
│ └───────────────────────────────────┘    │
│ ┌ 相处模式 ─────────────────────────┐    │
│ │ [会冷静下来再沟通；需要独处时间__] │    │
│ └───────────────────────────────────┘    │
│ 已改动 1 处 · [恢复标签默认]              │  ← 覆盖/回滚入口
│                                          │
│ 描述  [___________________________]      │
│                        [取消]  [创建]    │
└──────────────────────────────────────────┘
```

### 规则规格

| 项 | 规格 |
|---|---|
| **多选上限** | **3 个**。理由：`prompt_builder` 已有 `personality[:4]` 的硬上限、`mood_fusion.py:15` 用 `[:4]`、`life_summary.py:545` 用 `[:5]`——**4~5 是既有事实标准**，取 3 更保守且与「三组描述」数量对齐；选满后未选项 `disabled` + `title="最多 3 个"`，不静默截断 |
| **互斥组** | 至少声明两组：`话痨 ↔ 高冷`（说话量互斥）、`冷暴力 ↔ 温柔`（冲突模式互斥）。点新项时自动取消同组已选项 + 一行 `aria-live="polite"` 提示，**不弹窗、不阻断** |
| **三组描述可预览** | 折叠区「这些会写进 TA 的人设（可改）」，默认展开；每次点标签实时重算 |
| **可编辑** | 三组都是 `textarea`，`font-size: var(--text-base)`(16px)，与正文同档（修掉当前 16px > 正文 15px 的错档） |
| **可覆盖** | 用户手动改过的组打「已改」标记，**后续再点标签不覆盖已改的组**（手填优先原则，与后端 `setdefault` 一致），只更新未改的组 |
| **可回滚** | 「恢复标签默认」按钮：清空所有手动改动，按当前标签集重算 |
| **落点改契约内 key** | 见下表 |

### 翻译表重写（`config/persona_tags.json` → 新 schema）

**旧**：`{"温柔": {"speaking_style": {"语气": "温和耐心", "常用词": [...]}, "emotional_patterns": {...}}}` — 自由 key，与消费端无关

**新**：

```json
{
  "version": 2,
  "tags": {
    "温柔": {
      "group": "temperament",
      "conflicts": [],
      "preview": "说话轻，会先安抚对方情绪",
      "fields": {
        "speaking_style":       { "基础风格": "语气温和耐心，常用「好的」「慢慢来」" },
        "emotional_patterns":   { "压力反应": "先安抚对方，自己的情绪放后面" },
        "relationship_behavior": {}
      }
    },
    "话痨": {
      "group": "talkativeness",
      "conflicts": ["高冷"],
      "preview": "话多，经常连发好几条",
      "fields": { "speaking_style": { "基础风格": "话多，想到什么说什么，经常连发多条消息" } }
    },
    "傲娇": {
      "group": "temperament",
      "conflicts": [],
      "preview": "嘴上不认，行动上很在意",
      "fields": {
        "speaking_style":       { "基础风格": "口头禅「哼」「才不是」，嘴上不肯认" },
        "emotional_patterns":   { "爱的语言": "明明在意却装作不在乎，用行动表达" }
      }
    }
  }
}
```

**三条硬约束**（写进 schema 校验 + 单测）：

1. `fields` 的 key 只允许 `基础风格` / `依恋类型` / `压力反应` / `爱的语言` / `冲突模式` / `边界需求` —— **与 `promptFields.js:5-7` 和 `prompt_builder.py` 的读取契约逐字一致**。新增 key 必须先改契约，否则 CI 失败
2. `conflicts` 必须是双向声明（A 声明 B，B 也声明 A），单测校验对称性
3. `preview` ≤ 20 字，供 chip 的 `title` 与详情页展示

### 冲突合并规则（替换 `setdefault` 静默丢弃）

| 情况 | 旧行为 | 新行为 |
|---|---|---|
| 两个标签写同一 key，值不同 | 后到者被**静默丢弃** | 按选中顺序用「；」并列合并，如 `基础风格` = `语气温和耐心；话多，想到什么说什么` |
| 两个标签写同一 key，值相同 | 丢弃 | 去重保留一份 |
| 用户手动改过该 key | 保留手填（`setdefault`） | **保留手填，标签不再写入该 key**（行为不变，但要加「已改」标记让用户看得见） |
| 互斥标签同时选中 | 无感知 | 点选时自动取消同组项 + `aria-live` 提示 |

### 接口调整

| 接口 | 现状 | 建议 |
|---|---|---|
| `GET /api/persona/tags` | `{"tags": ["温柔", ...]}` 只有名字 | `{"tags": [{name, group, conflicts, preview}], "version": 2}`；保留 `tags` 为名字数组的兼容字段一个版本 |
| `POST /api/persona` | `{id?, name, description?, personality?}`，后端自己派生 | 增加可选 `derived?: {speaking_style, emotional_patterns, relationship_behavior}`。**有 `derived` 时以它为准**（用户编辑后的值），无则按新表派生 |
| `PATCH /api/persona/{id}` | `{fields: {...}}` 只改字段，不重派生 | 增加可选 `rederive: true`：按当前 `personality` 重算三组，手填 key 不动。详情页改性格后弹「要按新性格重算描述吗？」 |

**向后兼容**：老 persona 文件里的 `personality` 数组原样保留；新表只在 `POST`/`rederive` 时生效，不做批量迁移。

### 前端配套（`ContactsPage.svelte`）

| 位置 | 改法 |
|---|---|
| `:803-818` `.tag-cloud` | 补 `.tag-cloud` / `.tag-chip` / `.tag-chip.on` / `.tag-chip:disabled` / `.tag-hint` 五条规则（当前**零样式**，是最高优先级 bug） |
| 选中态 | 复用 `TabBar.svelte:145-155` 已验证的选中态语言：`color: var(--accent); background: var(--accent-wash); border-color: var(--accent-line)` + 左上角 1px `--accent` 描边；`on` 类要真的有效果 |
| 计数与上限 | 标题右侧 `已选 2/3`，用 `.micro-label`；到 3 时未选项 `disabled` |
| 三组预览 | 新增折叠区，三个 `prompt-dict` 表单（可直接复用 `PersonaField.svelte` 的 `prompt-dict` 渲染器，`promptFields.js` 已有 spec） |
| 详情页 `personality` | `type: 'list'`（每行一个）改为同一个 `.tag-cloud` 组件，与建人弹窗统一控件 |
| 创建后 | `showCreate=false` 前先展示一次「已写入：说话方式… / 情绪反应… / 相处模式…」toast 或详情页高亮，让用户知道发生了什么 |

## 1.5 分档结论对照（给决策用）

| 档位 | 做法 | 工作量 | 收益 | 建议 |
|---|---|---|---|---|
| A 保留原样 + 只补 CSS | 补 `.tag-chip` 样式，其余不动 | 0.5 天 | 用户能看见选中了，但仍不知道派生什么 | ❌ 治标 |
| **B 降级为预填草稿（推荐）** | 新 schema + 上限 3 + 三组可预览可编辑可覆盖 + 冲突并列合并 + 落点改契约内 key | 3~4 天（后端 1.5 + 前端 2） | 用户可控、派生 100% 生效、消灭静默丢弃 | ✅ |
| C 砍掉派生，标签只存 personality | 删 `apply_persona_tags` 调用，标签仅作为 `personality` 数组进 `性格上，你温柔、活泼。` | 0.5 天 | 简单、无矛盾 | ⚠️ 可作为 B 的降级兜底；但丢掉「三组描述」这个有价值的结构化输入 |
| D 加 LLM 实时生成三组描述 | 点标签 → 调模型生成 | 3 天 + 每次创建一次 LLM 调用 | 描述更自然 | ❌ 慢、贵、不可复现、离线不可用 |

**推荐 B**，并把 **C 作为兜底**：若 B 的后端改造排不上期，先做 C（删掉派生调用 + 补 chip 样式），至少立刻消除「用户以为生效实际没生效」的欺骗性。**A 不可接受**——它保留了欺骗，只修了可见性。

# 第二部分　前端 UI 视觉整改方案

## 2.1 现状诊断（全部为实测，非推测）

### 问题 2：层级没有阶梯，且两套语言并存

- **z-index 无 token、乱序（15 处裸值）**：`ChatPage.svelte:1734` 图片预览 `999`、`ChatPage.svelte:1374` 会话菜单 `200`、`AppDialog.svelte:74` `100`、`Toast.svelte:41` 与 `ChatPage.svelte:2042` `60`、`ContactsPage.svelte:1326` 与 `SettingsWechat.svelte:473` `50`、`ImmersiveShell.svelte:188/197`、`PhoneShell.svelte:144/152`、`ChatPage.svelte:2013/2021` 四组 `40/41`、`TopBar.svelte:23` `30`、`SettingsConversation.svelte:248` `10`。999 与 200 之间是一段无人区，任何新浮层都可能盖错。
- **阴影阶梯名存实亡**：全项目 `var(--shadow*)` 只用 8 处（`AppDialog.svelte:91`、`ConfigNotice.svelte:134`、`SamplingPresets.svelte:130/135`、`SettingsConversation.svelte:256`、`ChatPage.svelte:1380/2028`、`ContactsPage.svelte:1345`），另有 3 处**硬编码阴影**：`ImmersiveShell.svelte:204` `-8px 0 30px rgba(28,25,23,.1)`、`PhoneShell.svelte:158` `0 -8px 30px rgba(28,25,23,.12)`、`ChatPage.svelte:1722` `0 1px 3px rgb(0 0 0 / .18)`（`.chat-image`）。前两处暖黑在深色下变脏灰。
- **两种层级语言并存**：设置页已经用「细线分区」(`settings-base.css:33-40` `.card{background:transparent;border:none;border-top:1px solid var(--border-strong);box-shadow:none}`)，而 `.modal`(`ContactsPage.svelte:1338`)、`PersonaCard`、`StatePanel` 仍是「盒子 + 阴影」。同一个产品里，「层」到底靠线还是靠影，没有统一答案。

### 问题 3：「玻璃滥用」不成立——真实问题是玻璃完全缺席

- `backdrop-filter` **全项目 0 处**
- `--glass`(`tokens.css:136,187`) / `--glass-border`(`:137,188`) / `--glass-strong`(`:161,212`) / `--scrim`(`:160,211`) / `--blur`(`:315`) / `--blur-heavy`(`:316`) 共 **6 个 token 名、10 处定义，`grep "var(--glass"` 等全部 0 消费**。`tokens.css:315-316` 注释直白写着「毛玻璃 (已停用, 保留 token 兼容)」，`--blur: 0px`。对照 `--overlay` 有 6 处消费——说明浮层确实存在，只是没用玻璃
- 该用玻璃的地方全用了不透明色块：
  - `.overlay`(`ContactsPage.svelte:1323`)：`background: var(--overlay)` 无模糊、无入场动画
  - `.modal`(`:1338`)：`background: var(--surface)` 纯不透明 + 5px 圆角 + `--shadow-lg`
  - `.imm-drawer`(`ImmersiveShell.svelte:194-204`)：`background: var(--bg)` 纯不透明
  - `--topbar-bg` / `--tabbar-bg`(`tokens.css:302-305`)：注释「去毛玻璃」，直接 `var(--surface)`

→ **现状是「一次矫枉过正的去玻璃化」**：从可能滥用，直接退到零玻璃，中间那档「只在浮层用、只叠两层、带噪点」的正确形态从未出现。方案不是「加回玻璃」，而是**建立分层规范，只在 4 个位置用玻璃，其余一律不透明**。

### 问题 4：暗色主题丢掉了品牌色相

HSL 实测：

| token | light | dark |
|---|---|---|
| `--bg` | `#f4f1ec` H=**37°** S=27% L=94% | `#0f0f0f` H=**0°** S=0% L=6% |
| `--surface` | `#ffffff` H=0° | `#161616` H=**0°** S=0% |
| `--surface-2` | `#efeae2` H=**37°** S=29% | `#1e1e1e` H=**0°** S=0% |
| `--text-1` | `#1c1917` H=24° S=10% | `#ededed` H=**0°** S=0% |

「慕 · Ink」的品牌身份是**暖纸底（H≈37）+ 冷蓝点缀（H≈209）**。浅色下这个对比成立；**深色把暖端压成了纯中性灰（H=0）**，只剩冷蓝单腿走路。
→ 所谓「暗色不一致」，根因不是亮度不对，是**深色主题丢失了暖炭底色**，切换后像换了个产品。

### 问题 5：主题机制有实际 bug

- `main.js:7-11` 只认 `light`/`dark`，**默认 `light`**；`SettingsAppearance.svelte:25-28` 默认 `'system'`
- → 用户从未设置过主题时：**设置页 UI 显示「跟随系统」为选中态，实际 `main.js` 强制 light**。用户以为自己选了跟随系统，其实没有
- `main.js` **无 `matchMedia` 监听**：系统在 light/dark 间切换，页面不跟随（除非重进设置页点一次）
- `ThemeToggle.svelte:14-21` 直接翻转 light/dark 并写 `cc-theme`，**会把 `system` 覆盖成具体值**，与「跟随系统」模式互斥且无提示
- `index.html` 只有 `<html lang="zh-CN" data-theme="light">`，**无 `<meta name="theme-color">`、无 `color-scheme`** → 深色下浏览器原生 UI（滚动条、`<input>` 默认样式、地址栏）仍是浅色，形成一圈白边

**13 / 14 / 15 三档挤在 2px 内，占了 114 次使用**——这是「看不出层级」的直接原因。
**表单控件 16px 大于正文 15px**：`ContactsPage.svelte:1360`、`AppDialog.svelte:126/139`、`PersonaField.svelte:100/129` 都用 `var(--text-base)`，而 `body` 是 `0.9375rem`(15px)。输入框比正文还大，视觉上抢戏。
**700 字重孤例**：`.modal-title`(`ContactsPage.svelte:1349`) 用 `font-weight: 700`，全站其他标题是 500/600。

### 问题 7：间距节奏在组件层被侵蚀

**67 处魔法数字**（`*.svelte` 内，`gap|padding|margin*: Npx`）用裸 px 而非 `--space-*`，分布：`2px`×17、`6px`×16、`1px`×15、`3px`×6、`4px`×3、`10px`×3、`9px`×2、`7px`×2、`5px`×2、`8px`×1。重灾区：`MemoryPage.svelte` 9 处、`ChatPage.svelte` 9 处、`TodayPage.svelte` 5 处、`DiscoverPage.svelte` 5 处、`SettingsAppearance.svelte` 5 处、`ContactsPage.svelte` 4 处。典型：`ConfigNotice.svelte:75 gap:2px`、`StatePanel.svelte:280 gap:6px`、`PersonaAdvanced.svelte:157 padding:1px 7px`、`PersonaCard.svelte:79 gap:3px`、`PhoneShell.svelte:209 gap:9px`、`SettingsAppearance.svelte:178 padding:2px`、`ChatPage.svelte:1728 margin:2px 4px`。
→ **`1/2/3/6px` 四档合计 54 处，占 81%**——这正好是当前 4px 刻度缺的亚刻度，补 `--space-px`(1) / `--space-0-5`(2) / `--space-0-75`(3) / `--space-1-5`(6) 即可覆盖绝大部分。

### 问题 8：动效与无障碍支持缺失

- **`prefers-reduced-motion` 全项目 0 命中**。`Toast.svelte:13-19` 的 240ms 上浮、`--transition-spring`、`.skeleton` 的 1.4s shimmer 全部无视系统偏好
- **无 `prefers-contrast`**、**无 `forced-colors`**
- 焦点态：`tokens.css:381-385` 有一条全局 `:focus-visible { outline: none; box-shadow: var(--focus-ring) }`，另有 18 处组件级 `outline: none`（`AppDialog.svelte:142`、`PersonaField.svelte:114/140`、`Switch.svelte:69`、`ThemeToggle.svelte:69`、`ChatPage.svelte:1960`、`ContactsPage.svelte:911/1166/1364` 等）→ **全站焦点可见性 100% 依赖那个只有 1.9:1 的 `--focus-ring`**，等于所有输入框、按钮、开关在键盘操作下都没有可见焦点。这是无障碍上最严重的一处
- 弹窗**无入场动画**：`.overlay`/`.modal` 直接出现，而 `Toast` 有 240ms 过渡——动效语言不统一

## 2.2 方案一：色彩 token 体系

### 命名法

沿用现有 `Layer1 基础 / Layer2 语义 / Layer3 组件` 三层结构，不改架构，只**重定值 + 补阶梯**。新增一层 `--glass-*` 与 `--z-*`。

### Layer 2 语义色 —— 亮色（替换 `[data-theme='light']`）

```css
[data-theme='light'] {
  /* 背景 —— 保留暖纸色相 H≈37，把 bg 与 surface 的明度差从 6% 拉到 8% */
  --bg:            #f3efe8;   /* H38 S31 L93 */
  --surface:       #fdfbf8;   /* H36 S56 L98 —— 比纯白柔，去掉刺眼感 */
  --surface-2:     #ece6dc;   /* H37 S30 L89 */
  --surface-3:     #e0d8ca;   /* H38 S26 L84 */
  --surface-inset: #f6f2eb;   /* 输入框/凹槽 */

  /* 文字 —— 三档全部拉到 AA 以上 */
  --text-1:        #191613;   /* 17.44 on surface */
  --text-2:        #4d473f;   /*  8.88 */
  --text-3:        #665e53;   /*  6.18 —— 关键改动：原 #837b71 只有 4.17 */
  --text-inverse:  #fdfbf8;

  /* 边框 —— 分「装饰线」与「结构线」两档，结构线必须 ≥3:1 */
  --border:        #ded6c9;   /* 1.40 —— 仅装饰分隔，不承担边界语义 */
  --border-strong: #8c8170;   /* 3.70 —— 输入框/卡片边界，达标 */

  /* 强调 —— 冷蓝 H≈209 不动，只压深一档 */
  --accent:        #2b567f;   /* 7.42 on surface */
  --accent-strong: #1f4366;   /* 9.90 */
  --accent-soft:   #e6eef6;
  --on-accent:     #ffffff;   /* 7.66 on accent */

  /* 语义色 —— 全部满足 ≥4.5 on surface */
  --success:       #3d6b4c;   /* 5.97 */
  --warning:       #8a6626;   /* 5.07 */
  --error:         #98382f;   /* 6.91 */
  --info:          #2b567f;   /* 7.42 */
  --on-success:    #ffffff;   /* 6.17 on success */
  --on-warning:    #ffffff;   /* 5.24 */
  --on-error:      #ffffff;   /* 7.14 */

  /* 交互态 */
  --row-hover:     rgba(28, 22, 16, 0.045);
  --row-active:    rgba(28, 22, 16, 0.085);
  --focus-ring:    0 0 0 2px var(--surface), 0 0 0 4px var(--accent);  /* 双环：内白外蓝，7.42:1 */
  --overlay:       rgba(28, 22, 16, 0.38);
}
```

```css
  --accent:        #8ab3d8;   /* 7.99 on surface */
  --accent-strong: #a9cae8;   /* 10.33 */
```

### 深色色相一致性验收

整改后两套主题的 `--bg / --surface / --surface-2 / --text-1` 色相：

| token | light H | dark H | 差值 |
|---|---|---|---|
| bg | 38° | 30° | 8° ✅ |
| surface | 36° | 26° | 10° ✅ |
| surface-2 | 37° | 32° | 5° ✅ |
| text-1 | 30° | 37° | 7° ✅ |

验收标准：**任意主题的核心中性色 H 落在 24°~40°，且亮暗两套的 H 差 ≤12°**。当前现状是 dark 全为 H=0°，差 37°——这就是「换了个产品」的量化解释。

### 语义色统一规则（消灭 `--toast-*-text: #ffffff`）

**硬规则：禁止任何语义色配硬编码 `#fff`。** 统一为：

```css
--toast-bg:            var(--surface);
--toast-text:          var(--text-1);
--toast-success-bg:    var(--surface);
--toast-success-text:  var(--success);   /* 不是 #fff */
--toast-error-bg:      var(--surface);
--toast-error-text:    var(--error);
--toast-warning-text:  var(--warning);
--toast-info-text:     var(--text-1);
--toast-accent-bar:    currentColor;     /* 保留 Toast.svelte:56-72 左侧 2px 色条，色盲友好，设计正确 */
```

Toast 从「语义色实底 + 白字」改成「surface 底 + 语义色文字 + 左侧语义色竖条」。实测对比度：light success 5.97 / error 6.91 / warning 5.07；dark success 8.14 / error 7.09 / warning 8.85 —— 全部达标，且深色下不再出现 2.7:1 的白字。`Toast.svelte` 现有的 2px `currentColor` 竖条设计（`:56-72`）**保持不变**，它同时用形状和颜色两个通道表达状态，是对的。

## 2.3 方案二：glassmorphism 分层规范

### 总原则

1. **玻璃 = 层级语言，不是装饰**。只在「浮在内容之上、且需要让人看见底下还有内容」的表面用
2. **同时最多 2 层玻璃**（modal 压 drawer 已经是 2 层，不许出现第 3 层）
3. **玻璃上必须有不透明兜底**：`@supports not (backdrop-filter: ...)` 与 `prefers-reduced-transparency` 下退成 `var(--surface)`
4. **正文永不直接放在玻璃上**——玻璃上只放标题、按钮、元信息；长文本区一律 `var(--surface)`

### 材质四档

> **实施后的修正**：下表是**落地后的实测规格**。最初方案写的是 `.72/.74/.80/.82/.88/.88`，落地时用 `tools/check_contrast.py` 按 WCAG 公式逐档验算，发现 dark `glass-1` @.74 叠图片时 `text-3` 只有 **4.08:1**，因此把全部档位上调一档（`.78/.78/.84/.85/.90/.91`），并把 dark `text-3` 从 `#9a9287` 提到 `#a49b8f`。改完之后 `text-3` 在**全部档位、全部底层**都达标，「`text-3` 只能在 glass-3 上用」这条限制随之取消。

| 档 | 用途 | `backdrop-filter` | 背景 alpha（light / dark） | 边框 | 圆角 | 允许的文字 |
|---|---|---|---|---|---|---|
| `glass-0`（scrim） | 遮罩层 | `blur(2px)` | `rgba(28,22,16,.38)` / `rgba(0,0,0,.64)` | 无 | — | 无文字 |
| `glass-1`（chrome） | 顶栏 / 底栏 / 侧栏 / sticky 保存条 | `blur(10px) saturate(1.10)` | `rgba(253,251,248,.78)` / `rgba(28,24,21,.78)` | 底部 1px `--glass-border-2` | 0 | `text-1` / `text-2` / `text-3` |
| `glass-2`（sheet） | 抽屉 / 底部面板 / 弹出菜单 | `blur(18px) saturate(1.15)` | `rgba(253,251,248,.84)` / `rgba(28,24,21,.85)` | 全周 1px + 顶部 inset 高光 | 12px（sheet 顶角） | `text-1` / `text-2` / `text-3` |
| `glass-3`（modal） | 模态弹窗 | `blur(26px) saturate(1.20)` | `rgba(253,251,248,.90)` / `rgba(28,24,21,.91)` | 全周 1px + 顶部 inset 高光 | 8px | `text-1` / `text-2` / `text-3` |

**为什么 alpha 这么高（.78~.91）而不是常见的 .2~.4**：低 alpha 玻璃在暖纸底上会让文字对比度随底层内容剧烈波动。实测白 @.52 叠在 `#808080` 中位灰图片上，`text-3` 掉到 **3.58:1**（不达标）；@.78 回到 4.85:1，@.90 到 5.55:1。深色同理：@.52 时 `text-2` 只剩 4.07:1、`text-3` 2.87:1。

→ 结论：本项目只能做「厚玻璃」，不能做 Apple 那种「薄 vibrancy」。

**噪点已取消**：方案里原本给 `glass-3` 配了 `feTurbulence` 噪点。落地时判定不引入 —— 在 alpha ≥ .78 的厚玻璃上噪点几乎不可见，却要多一层合成与一个伪元素，收益为零成本非零。薄玻璃才需要噪点，而本项目配色撑不住薄玻璃。

### 性能与降级

```css
/* 1) 不支持 backdrop-filter 的浏览器 → 退成不透明 */
@supports not ((backdrop-filter: blur(1px)) or (-webkit-backdrop-filter: blur(1px))) {
  .glass-1, .glass-2, .glass-3 { background: var(--surface); }
  .glass-0 { backdrop-filter: none; }
}

/* 2) 系统要求降低透明度 → 全部退成不透明 */
@media (prefers-reduced-transparency: reduce) {
  .glass-1, .glass-2, .glass-3 { background: var(--surface); backdrop-filter: none; }
}

/* 3) 系统要求增强对比度 → 边框加粗、去玻璃 */
@media (prefers-contrast: more) {
  .glass-1, .glass-2, .glass-3 { background: var(--surface); backdrop-filter: none; border-color: var(--border-strong); }
}

/* 4) 减少动效 */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

**性能约束三条**：
1. `backdrop-filter` **只允许出现在 `position: fixed` / `sticky` 的元素上**，避免滚动时逐帧重绘大面积区域
2. **禁止在滚动容器内的列表项上用玻璃**（`ChatPage` 消息气泡、`ContactsPage` 列表行一律不透明）
3. **不写 `will-change: backdrop-filter`**——它会常驻合成层，反而更慢；只在入场动画期间由 class 临时加 `will-change: opacity, transform`

**噪点实现**：仅 `glass-3`（modal）使用，`::after` 绝对定位铺满 + `background-image: var(--glass-noise)` + `mix-blend-mode: overlay` + `opacity: 0.035` + `pointer-events: none`。`glass-1`/`glass-2` 不加噪点——顶栏和抽屉面积大，噪点在 Retina 上会变成可见颗粒。

## 2.5 方案四：圆角与阴影阶梯

### 圆角：7 档 → 5 档

「慕 · Ink」的设计原则写着「圆角克制 2~6px」，但实际有 `2/3/4/5/6/8/999` 七档，其中 3/4/5 三档在 2px 内，肉眼不可辨，纯属噪声。

```css
--radius-xs:   2px;    /* chip、头像、tag、进度条 —— 最锐利档，保留 */
--radius-sm:   4px;    /* 按钮、输入框、Toast */
--radius-md:   8px;    /* 卡片、弹窗、popover */
--radius-lg:  12px;    /* sheet、抽屉顶角、大面板 */
--radius-full: 999px;  /* 仅 pill 与 switch 滑块 */
```

`--radius`(4)、`--radius-xl`(8) 保留为别名。**规则：小元素用小圆角、大元素用大圆角**（当前 `.modal` 用 5px、`.avatar` 用 2px，尺寸感反了）。`--card-radius` 从 `--radius-lg`(6) 改为 `--radius-md`(8)。

### 阴影：5 档，与玻璃档位一一对应

```css

--shadow-1: 0 1px 2px rgba(28, 22, 16, 0.04);              /* 微抬升：chip hover */
--shadow-2: 0 2px 8px rgba(28, 22, 16, 0.06);              /* 下拉菜单、popover */
--shadow-3: 0 8px 24px rgba(28, 22, 16, 0.10),
            0 1px 3px  rgba(28, 22, 16, 0.06);             /* 抽屉、sheet */
--shadow-4: 0 20px 48px rgba(28, 22, 16, 0.16),
            0 2px 8px   rgba(28, 22, 16, 0.08);            /* 模态弹窗 */
--shadow-focus: var(--focus-ring);                         /* 焦点环，独立一档 */

/* 深色：换成纯黑 + 更强 alpha + 一道内高光（否则阴影在深底上完全不可见） */
[data-theme='dark'] {
  --shadow-1: 0 1px 2px rgba(0, 0, 0, 0.30);
  --shadow-2: 0 2px 8px rgba(0, 0, 0, 0.40);
  --shadow-3: 0 8px 24px rgba(0, 0, 0, 0.50), inset 0 1px 0 rgba(255, 245, 230, 0.06);
```

**关键改动：深色阴影从暖黑 `rgba(30,27,24,x)` 换成纯黑 `rgba(0,0,0,x)` + 内高光。** 暖黑在 `#1c1815` 的深底上会变成偏黄的脏晕；纯黑 + 顶部内高光才能表达「浮起来」。

| 元素 | 入场 | 退场 |
|---|---|---|
| scrim | `opacity 0→1`, 140ms, `--ease-out` | 90ms, `--ease-in` |
| modal | `opacity 0→1` + `scale .97→1` + `translateY 8px→0`, 280ms, `--ease-out` | 120ms, `--ease-in` |
| drawer | `translateX 100%→0`, 200ms, `--ease-out` | 140ms, `--ease-in` |
| popover | `opacity 0→1` + `translateY -4px→0`, 140ms, `--ease-out` | 90ms |
| chip 选中 | `background/border-color` 90ms, `--ease-out`（**不加 scale**，冷峻风格） | 同左 |
| toast | 保留 `Toast.svelte:13-19` 的 240ms `1-(1-t)³` | 同左（设计正确，不动） |

**规则**：退场时长 = 入场时长 × 0.6。入场用 `--ease-out`（快起慢收），退场用 `--ease-in`（慢起快收），这是「出现要稳、消失要快」的通用解。

**`.pressable:active { transform: scale(0.98) }`** 保留，但补 `transition: transform var(--dur-1) var(--ease-out)`——当前无 transition，按下是硬跳。

## 2.7 对标参考（站点 + 可借鉴的具体手法）

| 站点 | 可借鉴的具体手法 | 对应到本项目 |
|---|---|---|
| **Linear** (linear.app) | 深色用「中性灰 + 单一强调色」，层次全靠 `1px` 半透明边框（`rgba(255,255,255,.06)`）+ `inset 0 1px 0` 顶部高光，**全站零 box-shadow** | 直接印证「细线分层」路线；把 `--glass-highlight` 与 `--border` 分层做对，就能不加阴影出层级 |
| **Raycast** (raycast.com) | 玻璃浮层必带**噪点纹理**（约 3~5% 不透明度），消除大面积模糊的「塑料感」；圆角阶梯 6/10/14 与元素尺寸严格对应 | 本项目 `glass-3` 加噪点、圆角阶梯重排为 2/4/8/12 |
| **Vercel** (vercel.com) | 顶栏玻璃只在滚动时启用；玻璃底部用 1px **渐变边**（中间亮两端透明）代替实线 | `TopBar` 玻璃化时用渐变边；未滚动时保持不透明 |
| **macOS / iOS 的 Material** | 材质分 `ultraThin / thin / regular / thick` 四档，**规定同时最多两层**，且「文字永不直接放在 thin 材质上」 | 直接采纳为本项目的四档 + 两层上限 + 「正文不上玻璃」规则 |
| **Arc Browser** | 侧栏玻璃 + 内容区不透明，**玻璃只用于 chrome，不用于 content** | `ImmersiveShell` 抽屉玻璃化，`main-area` 保持 `--surface` 不透明 |
| **Stripe Dashboard** | 语义色只在状态点上用**极小面积**，不用语义色铺背景；toast 用「白底 + 语义色左条 + 语义色文字」 | 直接采纳为本项目 toast 新规格（替换语义色实底 + 白字） |
| **Notion** | 正文 16px / 行高 1.6 / 行宽 46~75 字符；界面元素 14px；两级字号差 2px | 正文提到 16px/1.65/68ch，UI 14px，与 Notion 完全对齐 |
| **Radix Colors** (radix-ui.com/colors) | 12 级色阶命名（step 1~12），1~2 背景、3~5 组件、6~8 边框、9~10 实心、11~12 文字；**每级都有明确的语义槽位** | 本项目虽不引入 12 阶，但可采用「每档必须声明用途」的规则——`--surface-3` 只能做装饰底、`--border` 只能做装饰线 |
| **Tailwind / shadcn 的 token 命名** | `background / foreground / card / muted / border / ring` 语义命名法 | 现有 `bg/surface/text/border/accent` 已接近，补 `--ring`（焦点环）语义槽 |

**不建议参考的**：Apple 官网那种低 alpha（.2~.4）大玻璃 —— 实测在暖纸底 + 图片背景上会让文字掉到 3.5:1 以下，与本项目的可读性要求冲突。

# 附录 B · 实施结果（2026-10-23 收尾）

> 本方案已按「质量优先」全量落地。以下记录**与方案原文不一致的地方**及原因 ——

## B.1 第一部分：性格字段（已落地）

结论采用方案 1.3 的**降级为预填草稿**，未采用 A 档（保留原样）或 C 档（整块砍掉）。

### 实施中修正的三处方案偏差

| 方案原文 | 实际实施 | 原因 |
|---|---|---|
| 落点 `speaking_style["基础风格"]` | 同 | 核查消费方契约后确认唯一正确落点：`prompt_builder.py:198` 只读 `基础风格`，其它 key 全丢 |
| 落点 `emotional_patterns[...]` | `emotional_patterns["情感表达"]` | 三个结构化 key（依恋类型/压力反应/爱的语言）会被模板拼成「压力大时会善于安抚对方情绪」这种病句；草稿是**完整句子**，必须走 `情感表达` 原样成句分支（`prompt_builder.py:232`） |
| 落点 `relationship_behavior[...]` | `relationship_behavior["相处模式"]` | 同上，走 `prompt_builder.py:276` 的原样成句分支 |

`core/persona/tags.py` 双 schema：v1 保持 `setdefault` 语义（向后兼容 CLI `setup_wizard.py:439-466`），
v2 支持合并 + 互斥组 + 上限。新增 `apply_drafts()`，在 `apply_persona_tags()` **之后**执行 ——
顺序反了就等于「标签覆盖用户」，预览失去意义。

### 端到端实测

```
POST /api/persona/tags/preview  {"tags":["温柔","傲娇","爱吃醋"]}
  → speaking    : 语气温和耐心，常用「好的」「没事的」「慢慢来」；常用「哼」「才不是」…
  → emotion     : 善于安抚对方情绪，自己不开心时也倾向于先平静下来再说话；…
  → relationship: 会主动照顾对方的情绪，起争执时习惯先退半步；…

POST /api/persona  {..., "drafts": {...emotion 手动补一句...}}
GET  /api/persona/{id}/advanced
  → speaking_style      {"基础风格": "…"}           ✅
  → emotional_patterns  {"情感表达": "…（用户手动补的一句）"}  ✅ 用户改动保留
  → relationship_behavior {"相处模式": "…"}          ✅
```

生成的 system prompt 实际渲染：
```
你是小月，20岁，女生。性格上，你温柔、傲娇、爱吃醋。你说话语气温和耐心，…。
情绪上，你善于安抚对方情绪，…（用户手动补的一句）。
你和对方的关系：…。相处上，你会主动照顾对方的情绪，…
```
三段全部进入 prompt，且**没有**被套成病句模板。

### 实施中发现的两个真 bug（方案未预见）

1. **草稿 textarea 被裁**：`rows="2"` 是固定高度，后端草稿常有 60~120 字，
   末行被切掉半行 —— 用户看不到自己即将保存什么。修法：`use:autoGrow` action，
   并且要补上上下边框（`scrollHeight` 不含 border，border-box 下直接写会少 2px）。
2. **`/api/persona/{id}` 不返回这三个字段**：它们属于 `ADVANCED_FIELDS`，
   只能从 `/api/persona/{id}/advanced` 读。排查时若只查前者会误判为「草稿没落库」。

## B.2 第二部分：视觉整改（已落地）

### 与方案最大的偏差：玻璃被**重做**了两次

方案原文第 2.x 节给的是「四档玻璃 + 提高 alpha 保可读性」。
第一次实施后用户反馈「没什么变化」—— 查下去发现方案**漏了一个前提**：
`--bg` 是纯色，`backdrop-filter: blur()` 对纯色的输出还是纯色，
alpha 从 .72 调到 .90 视觉上毫无差别。

真正的解法是**先造氛围层**（`--ambient-*` 铺在 `body::before`），玻璃才有东西可模糊。
详见 `docs/设计语言_Ink.md` 阶段六。

三个叠加根因（按发现顺序）：
1. 氛围层缺失 —— 玻璃底下没内容
2. 色团锚在四角 + transparent 停在 62% —— 内容区中心落在透明区外，正中一片纯白
3. 色团边界太柔 —— 20px+ 模糊把 200px 内平缓渐变抹平成纯色

以及一个**流程性**根因：改了源码但没 `npm run build`，服务器一直发 `webui/static/assets/`
里的旧产物，前两轮截图全部无效。

### 方案里被推翻的一条

> 「`--blur` / `--blur-heavy` 归零，**停用毛玻璃**」（`设计语言_Ink.md:53`，阶段一）

本轮回滚了这条决策。理由：当时停用毛玻璃是因为「玻璃底下没有内容、糊出来是纯色」，
那个问题现在通过氛围层解决了。**玻璃本身没问题，缺的是背景。**
已在 `设计语言_Ink.md` 阶段六开头显式记录这次推翻，避免后来的人误判为回退。

### dark 的 alpha 硬下限 .70

想让 dark 更透（.64）被两道守卫拦下：
- `tests/test_design_tokens.py::test_glass_alpha_is_thick_enough` 断言 ≥ 0.70
- `tools/check_contrast.py`：dark 下 `text-3` 压 glass-1、玻璃底下是最亮内容时只有 3.93:1

结论：**环境光要靠加浓色团来补，不是靠减薄玻璃。**
同时把 dark 的 `--text-3` 从 `#a49b8f` 提到 `#b3aa9c`（6.44 → 7.09 on surface）。

### 间距层：方案未覆盖的一档

验收要求「硬编码 gap/padding/margin 为 0」，但替换时发现 87 处落在 1~3px，
4px 节奏覆盖不到（chip 内边距、图标-文字缝、基线微调）。补 `--optical-*` token 层，
由 `tools/fix_spacing.py` 机械替换。详见 `设计语言_Ink.md` 第八节。
